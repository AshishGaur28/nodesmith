== 1. Executive Summary & Scope

`SPEC-03` specifies the rules, template architectures, code synthesis transformations, and target code emission standards for turning the canonical Intermediate Representation (IR) AST (`SPEC-00`) into production-grade target source code.

Supported target output targets include:

* **C++17 / C++20 (`rclcpp`):** High-performance, zero-allocation runtime paths, header/source separation, CMake/ament_cmake package layouts.
* **Python 3 (`rclpy`):** Idiomatic, readable code using standard ROS 2 setup package structures.

== 2. Code Generation Invariants & Guarantees

1. **Determinism:** Given identical IR (same IR hash, `SPEC-00` §5), target language and generator version (which includes pinned formatter versions), code synthesis MUST yield bit-for-bit identical source code across all operating systems.
2. **Zero Manual Modification Rule:** Synthesized source files are immutable outputs of the build system. User-customized logic must be attached via SPEC-02 expression definitions or linked modular block headers—never edited directly in generated outputs.
3. **Target Parity:** Code generated for standard publisher, subscriber, service, parameter, and timer logic across C++ and Python must satisfy identical functional behavioral tests. In v1 the Python target supports only the core blocks and `concurrency` (`SPEC-01` §5.1 rule 7, `ERR_SEM_114`); extension parity for Python is the first work after v1.
4. **Clean Abstractions:** Target source files MUST NOT embed generic template strings or leftover generator variables. Generated output must look like hand-crafted, clean idiomatic source code.

=== 2.1. RMW Binding

The RMW is a generation-time choice (`node.rmw`, `--rmw`, `SPEC-01` §4.1), never a run-time one. The generator emits a package for exactly one RMW and nothing else:

1. The generated `package.xml` has one `<exec_depend>` on that RMW's package (`rmw_fastrtps_cpp` for `fastrtps`) and none on any other RMW.
2. Generated sources use only the client-library API (`rclcpp`, `rclpy`). They contain no RMW-specific header, symbol or `RMW_IMPLEMENTATION` handling, so adding an RMW later means adding a table row and a package dependency, not changing the manifest or the IR.
3. Features that depend on the RMW are checked against this capability table at generation time. The row for an unsupported feature is an error with the feature's own code; nothing is emitted "best effort".

[cols="1m,1,1,1", options="header"]
|===
| RMW | Loaned messages (`zero_copy`, `SPEC-06`) | `shared_memory.middleware_backend` values | Security enclaves (`SPEC-08`)
| `fastrtps` | Fixed-size types only | `rmw_default` | Yes
|===

A `middleware_backend` the chosen RMW does not list (for example `iceoryx` with `fastrtps`) is `ERR_SHM_001`.

Only `fastrtps` exists in v1; `cyclonedds` and `zenoh` are reserved. The later phase that makes the RMW configurable adds rows and their per-RMW generation rules here.

*Unverified against a ROS distribution (check before templating):* that `rmw_fastrtps_cpp` is the sole RMW package the generated package needs to declare on Jazzy, and the capability row values.

== 3. Type & Symbol Mapping Matrix

To ensure target language compatibility, IR primitive types map strictly according to the following matrix:

[cols="1m,2m,2m", options="header"]
|===
| Canonical IR Type | C++ Target (`rclcpp`) | Python Target (`rclpy`)

| `bool`
| `bool`
| `bool`

| `int64`
| `int64_t`
| `int`

| `float64`
| `double`
| `float`

| `string`
| `std::string`
| `str`

| `int32`
| `int32_t`
| `int`

| `float32`
| `float`
| `float` (stored as double; rounded to 32 bits at every `float32` sink)

| `bytes`
| `std::vector<uint8_t>`
| `bytes`

| `T[]` (array of a scalar `T`)
| `std::vector<T>`
| `list[T]`
|===

The canonical type set is defined once in `SPEC-02` §2.1; this matrix must cover exactly those types. Integer arithmetic wraps at operand width on all targets (`SPEC-02` §6), so the Python generator must emulate/wrap explicitly.

== 4. C++ Target (`rclcpp`) Emission Architecture

=== 4.1. File Hierarchy Standards
Generated C++ packages adhere strictly to `ament_cmake` standards:

[text]
----
<node_name>/
├── CMakeLists.txt
├── package.xml                # exec_depend on the chosen RMW only (§2.1)
├── config/
│   └── <node_name>.params.yaml  # only with parameters: every parameter with its manifest default (§4.5)
├── launch/
│   └── <node_name>.launch.py    # starts the node, with the parameter file when there is one (§4.5)
├── include/
│   └── <node_name>/
│       ├── pipelines.hpp      # Params, State, validate() and one eval_<pipeline>() per pipeline: plain C++, no ROS
│       ├── runtime.hpp        # SnapshotRing, RunGate (SPEC-12) + numeric helpers and DiagRing: no ROS
│       ├── logic_api.hpp      # the functions the user writes, only when the manifest declares functions (§4.4)
│       └── <node_name>_node.hpp
├── logic/                     # only with functions: a copy of the user's folder (§4.4)
└── src/
    ├── <node_name>_node.cpp   # the ROS glue: interfaces, parameters, commit and publish
    ├── logic_defaults.cpp     # only with functions: weak placeholders for everything in logic_api.hpp (§4.4)
    └── main.cpp
----

The split is what makes the generator testable: `pipelines.hpp` and `runtime.hpp` need only a C++ compiler, so the numeric semantics of `SPEC-02` are checked on random inputs against a reference interpreter on any machine (`tests/integration/test_cpp_semantics.py`). Only the glue needs ROS.

=== 4.2. Memory & Real-Time Guarantees
* **Pre-allocation:** All buffers, QoS profiles, subscriber/publisher handles, state objects and callback groups MUST be created during node initialization (constructor, or `on_configure` for lifecycle nodes, `SPEC-05`) and never inside a callback.
* **Zero Allocation in Callbacks:** With `realtime.enabled` (`SPEC-10`), callback paths MUST NOT allocate (no `new`, `make_shared`, container growth, string building, or logging). Without it, allocation is permitted but discouraged, and the generator keeps to preallocated message objects where the message type allows.
* **RAII Encapsulation:** Resource acquisition, thread handles, and ROS callbacks use strict RAII wrappers.

=== 4.3. Execution of a Pipeline

Each pipeline has a pure function `eval_<pipeline>(in, params, state, now_sec, dt_sec, out)` in `pipelines.hpp` (steps 1 to 4 of `SPEC-02` §7) and a method `run_<pipeline>` in the node (steps 5 and 6):

1. `run_<pipeline>` enters the run gate, pins one parameter snapshot for the whole execution (`SPEC-12` §5), and samples the clock once (`now_sec`, `dt_sec`).
2. `eval_<pipeline>` evaluates the DAG in creation order. A `let` becomes a `const` local, evaluated eagerly; every other node is inlined into its consumer, so `?:`, `&&` and `||` evaluate only the branch taken. Integer `+ - *` wrap, `/` and `%` fault on zero, and every helper sets a `fault` flag instead of throwing. Values reaching a state write or a message field are checked (NaN/Inf, narrow ranges). It returns `false` on any fault and writes the staged values into `out`.
3. On `false`, the node reports `ERR_RUN_101` into a preallocated ring (drained once a second into a `/diagnostics` message) and returns: no state change, no publication, a service answers with a default response.
4. Otherwise the node commits the staged state writes, then builds one value-initialised message per publisher named in `output_mapping`, in ascending publisher-id order, assigns the mapped fields and publishes.

Node-level rules:

* A subscriber that triggers several pipelines gets one subscription per pipeline, because the pipelines may sit in different callback groups (`SPEC-12` §3).
* Timers are created with `rclcpp::create_timer` on a steady, system or ROS clock; a firing that arrives while the previous execution still runs is skipped and reported as `ERR_RUN_102`. `startup` pipelines run once at the end of the constructor.
* `time` and `duration` fields are converted as `SPEC-02` §2.1 defines. Fixed-size ROS arrays (`T[N]`) are not supported: manifests declare `T[]` only, which maps to `std::vector`.
* The generated `CMakeLists.txt` compiles with `-ffp-contract=off` so that float results do not depend on the compiler's fused multiply-add (`SPEC-02` §6).
* The first line of each generated file names the IR hash, not the manifest path, so the same IR always yields the same bytes.
* In this revision the generator refuses manifests that enable an extension block (`lifecycle`, `shared_memory`, `security`, `telemetry`, `realtime`, `simulation`), `zero_copy` endpoints, and parameter types other than `bool`, `int32`, `int64`, `float32`, `float64`, `string`, `bool[]`, `int64[]`, `float64[]`, `string[]` and `bytes`.

The complete output for each supported example is checked in under `tests/golden/` and shown here. `examples/02_filter_pipeline.toml` gives:

[source,cpp]
----
include::../../tests/golden/02_filter_pipeline/include/imu_filter_node/pipelines.hpp[]
----

and the node source:

[source,cpp]
----
include::../../tests/golden/02_filter_pipeline/src/imu_filter_node_node.cpp[]
----

*Unverified against a ROS distribution (check before relying on it):* `rclcpp::QoS(5).best_effort()` chaining; that `rclcpp::create_timer(this, clock, rclcpp::Duration, callback, group)` accepts `this` and a `Duration`; `OnSetParametersCallbackHandle` as a member type of `rclcpp::Node`; `create_service` with `rclcpp::ServicesQoS()` and a callback group; `declare_parameter<T>` returning the override-aware value; and that callback groups created before the node is added to an executor are picked up. The generated glue compiles and behaves against a local stand-in for these signatures (`tests/support/ros_stub/`); the `jazzy` CI job is the check against the real ones.

Builds with `realtime.enabled` (`SPEC-10`) keep preallocated message objects and reset them to their defaults instead of declaring locals, so no allocation happens on the callback path (not implemented yet).

=== 4.4. User Logic

For the functions declared under `[[functions]]` (`SPEC-01` §4.9) the user writes plain functions in a `logic/` folder: no `main()`, no build files, no ROS code, no class to inherit. The generated package stays self-contained and fully regenerated; the user's files are copied into it and built with it.

`include/<node_name>/logic_api.hpp` declares, in the global namespace `logic`, one free function per declared function, plus two optional hooks. The arguments and the return value use the C++ types of §3 (scalars by value, strings and arrays by const reference), and a final `bool & fault` parameter lets the implementation abort the execution:

[source,cpp]
----
namespace logic {
void setup();     // optional: runs once, after a valid start-up and before any pipeline can run
void teardown();  // optional: runs once, when the node is destroyed
/// Chooses a target speed from the distance ahead, the limit and the previous speed.
double plan_speed(double distance, double limit, double previous, bool & fault);
}
----

* A pipeline calls `::logic::plan_speed(..., fault)` and treats `fault` as a numeric fault (`SPEC-02` §7 step 6). The node calls `logic::setup()` at the end of construction and `logic::teardown()` from its destructor.
* `src/logic_defaults.cpp` defines weak placeholders for `setup`, `teardown` and every declared function. The user's strong definition replaces a placeholder at link time. A function that is missing, or whose signature differs from the header (so that it is only an overload), leaves its placeholder in use: it prints `logic::<name> is not implemented` to standard error once and sets `fault`, so the pipeline stops with `ERR_RUN_101` instead of computing with an invented value. `setup` and `teardown` default to doing nothing.
* The package is one executable with a generated `main.cpp`. Its `CMakeLists.txt` globs `logic/*.cpp`, `*.cc` and `*.cxx` (`CONFIGURE_DEPENDS`) and puts `logic/` on the include path.
* `generate` reads the folder given by `--logic-dir` (default: `logic/` next to the manifest) and copies its `.cpp`, `.cc`, `.cxx`, `.hpp` and `.h` files, in path order, into the package's `logic/`. When that folder does not exist, `generate` first writes a starter `logic.cpp` into it, once, with one function per declaration whose body sets `fault` (so it builds and stops loudly until implemented). An existing folder is never modified: from then on it belongs to the user and Nodesmith never writes to it (`SPEC-04` §2.2).
* After a manifest change, `generate` prints a note for each declared function whose name does not appear as `name(` in the user's files. This is a hint only; the placeholders are the safety.
* The functions are plain C++ with no ROS dependency, so they can be unit-tested on their own.
* A node without functions is unchanged: it has no `logic_api.hpp`, `logic/` or `logic_defaults.cpp`.

=== 4.5. Runtime Configuration

Nothing is read from the manifest at run time. What can change without regenerating is what ROS already provides, and the package makes it easy to use:

* `config/<node_name>.params.yaml` lists every parameter with its manifest default under `/**: ros__parameters:` (so it applies under any node name or namespace) and is installed to `share/<node_name>/config/`. A user copies it, edits the values and passes it with `--ros-args --params-file`, or through the launch file; ROS parses it. Empty array defaults are written as comments, because YAML cannot give an empty list an element type. Values go through the same `validate()` as the manifest defaults: an invalid value makes the node refuse to start.
* `launch/<node_name>.launch.py` runs the node and passes the parameter file when the node has parameters (`ros2 launch <node_name> <node_name>.launch.py`).
* Parameters can also be set with `-p name:=value` at start-up and, unless `read_only`, with `ros2 param set` while running (`SPEC-07` §3.1). Topic and service names can be remapped with `-r`.
* Topics, QoS, pipelines, formulas, callback groups and threads are fixed at generation time.

== 5. Python Target (`rclpy`) Emission Architecture

=== 5.1. File Hierarchy Standards
Generated Python packages conform to standard ROS 2 `ament_python` structures:

[text]
----
<node_name>/
├── package.xml
├── setup.py
├── setup.cfg
└── <node_name>/
    ├── __init__.py
    ├── node.py
    └── runtime.py         # RunGate, DiagRing, low_pass (SPEC-12)
----

=== 5.2. Reference Output Template Snippet (Python Node)

[source,python]
----
# Generated by nodesmith (SPEC-03). DO NOT EDIT DIRECTLY.
import math
from dataclasses import dataclass, replace

import rclpy
from rcl_interfaces.msg import SetParametersResult
from rclpy.callback_groups import MutuallyExclusiveCallbackGroup
from rclpy.node import Node
from rclpy.qos import HistoryPolicy, QoSProfile, ReliabilityPolicy
from sensor_msgs.msg import Imu
from std_msgs.msg import String

from imu_filter_node import runtime as r2d  # low_pass, RunGate, DiagRing (SPEC-12)


@dataclass(frozen=True)
class Params:  # immutable snapshot; replaced by a single assignment (SPEC-12 §5)
    alpha: float = 0.85
    max_accel: float = 20.0


class ImuFilterNode(Node):

    def __init__(self):
        super().__init__('imu_filter_node', namespace='/sensors/chassis')
        self._params = Params()
        self._state_prev_z = 0.0  # touched only by callback group state_domain_1 (SPEC-12 §3)
        self._gate = r2d.RunGate()
        self._diag = r2d.DiagRing(self)
        self._declare_parameters()
        self._create_interfaces()
        self._gate.open()

    def _declare_parameters(self):
        self.declare_parameter('alpha', 0.85)
        self.declare_parameter('max_accel', 20.0)
        self.add_on_set_parameters_callback(self._on_set_parameters)

    def _on_set_parameters(self, updates):
        # Validate the whole batch, then swap one immutable object: all or nothing.
        nxt = self._params
        for p in updates:
            if p.name == 'alpha':
                if not 0.0 <= p.value <= 1.0:
                    return SetParametersResult(successful=False, reason="'alpha' out of range [0.0, 1.0]")
                nxt = replace(nxt, alpha=float(p.value))
            elif p.name == 'max_accel':
                if p.value < 0.0:
                    return SetParametersResult(successful=False, reason="'max_accel' below minimum 0.0")
                nxt = replace(nxt, max_accel=float(p.value))
        self._params = nxt
        return SetParametersResult(successful=True)

    def _create_interfaces(self):
        self._group_state_domain_1 = MutuallyExclusiveCallbackGroup()
        qos = QoSProfile(history=HistoryPolicy.KEEP_LAST, depth=5,
                         reliability=ReliabilityPolicy.BEST_EFFORT)
        self._raw_imu_sub = self.create_subscription(
            Imu, '/sensor/imu/raw', self._filter_imu, qos,
            callback_group=self._group_state_domain_1)
        self._filtered_imu_pub = self.create_publisher(Imu, '/sensor/imu/filtered', 10)
        self._status_pub = self.create_publisher(String, '/sensor/imu/status', 10)

    def _filter_imu(self, msg: Imu):  # pipeline `filter_imu` (SPEC-02 §7)
        with self._gate.scope() as run:
            if not run:
                return
            params = self._params  # one snapshot for the whole execution
            z = r2d.low_pass(msg.linear_acceleration.z, self._state_prev_z, params.alpha)
            over = abs(z) > params.max_accel
            next_prev_z = z
            if not math.isfinite(z) or not math.isfinite(next_prev_z):
                self._diag.report('ERR_RUN_101', 'filter_imu')
                return
            self._state_prev_z = next_prev_z  # commit
            out = Imu()
            out.header.frame_id = msg.header.frame_id
            out.linear_acceleration.z = z
            self._filtered_imu_pub.publish(out)
            status = String()
            status.data = 'OVERLIMIT' if over else 'OK'
            self._status_pub.publish(status)


def main(args=None):
    rclpy.init(args=args)
    node = ImuFilterNode()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.shutdown()


if __name__ == '__main__':
    main()
----

== 6. Template Engine Integration & Build Pipeline

1. **Jinja2 Architecture:** The toolchain is implemented in Python 3.11+ and renders Jinja2 templates. Target templates are decoupled file groups in `templates/cpp_rclcpp/` and `templates/python_rclpy/`.
2. **Context Injection:** Generator modules (`src/nodesmith/generators/<language>/`) ingest the `SPEC-00` AST models, build a target-specific context dictionary, and execute template expansion.
3. **Formatting Post-Process Hooks:**
   * **C++:** Formatted via `clang-format` before writing to disk.
   * **Python:** Formatted via `ruff format`.
