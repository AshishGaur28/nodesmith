= Implementation Plan
:toc:

Scope: everything up to and including generation. Deployment, benchmark running and CI are out (see `specs/INDEX.adoc`).

The order follows one rule: nothing is built on a config surface that can still change. The manifest is finalised first (M0). The toolchain stages then follow in pipeline order.

== M0. Finalise the config (manifest and IR contract)

Goal: `manifest_version = "1"` is frozen. After M0, a change to the manifest schema is a version bump, not an edit.

Work:

. *Pin the target.* Decided: ROS 2 Jazzy, with its default RMW. The manifest has no RMW field and generated code uses only client-library APIs, so the RMW becomes configurable in a later phase without a manifest change. Rust is deferred to a later release. The RMW is chosen at generation time (`node.rmw`, only `fastrtps` in v1) and the package is generated for that RMW alone (`SPEC-03` §2.1). Every "Unverified against a ROS distribution" note in SPEC-03 and 05-11 depends on it, and it decides which manifest fields are valid (loaned messages, lifecycle for `rclpy`).
. *Per-language feature support.* Decided: in v1 C++ supports every block and Python supports the core blocks and `concurrency` only; an enabled extension block with a Python target is `ERR_SEM_114`. Python extensions are the first work after v1. Rust is not a target.
. *Review each manifest block against real use.* Walk all eight examples (`07` service-heavy and `08` startup/subscriber/timer were added for this review) and, ideally, one node written by someone other than the spec author. Every field that was needed but missing, or present but never used, is resolved now.
. *Freeze the format.* TOML, YAML and JSON must produce the same IR hash for the same content. Decided in SPEC-01 §2: no YAML anchors, aliases or merge keys, no duplicate keys, JSON number grammar only, unknown keys rejected except `x-` keys.
. *Freeze the schemas.* `node_manifest.schema.json` and `node_ir.schema.json` get a version tag. The error registry (46 codes) is closed except for additions.
. *Build the conformance corpus.* Valid manifests with expected IR JSON and hash, and invalid manifests with the expected error code. Start from the 6 examples and the 28 negative cases already written. This corpus is the test suite for every later milestone.

Exit: `python conformance/verify.py` passes, the decisions in items 1 and 2 are written into SPEC-01/SPEC-03/INDEX, and `SPEC-00`, `SPEC-01`, `SPEC-02`, both schemas and the registry are Frozen (`specs/INDEX.adoc` §7).

Status: *done.* The corpus is `conformance/` (8 valid manifests with expected IR and hash, YAML and JSON copies of all 8, and invalid cases covering every manifest-triggerable build code; counts have grown since, see `conformance/`). Building it found and fixed eight spec gaps; see the M0 record below.

=== M0 record: gaps found while building the corpus

. `ERR_SEM_101` and `ERR_SEM_103` overlapped. Now: 103 only for a local that references itself; a local used before its `let` is 101.
. `ERR_SHM_003` used an undefined `sizeof(message)`. Now: the sum of declared leaf field sizes, a stated lower bound.
. `middleware_backend = "iceoryx"` cannot work with the `fastrtps` RMW (example 04 and SPEC-06 used it). Now `ERR_SHM_001`, with a per-RMW backend table in `SPEC-03` §2.1.
. `ERR_SIM_001` had no block-level flag to satisfy. Now `simulation.enabled_in_production`.
. `ERR_SEC_303` named no restricted topics. Now a listed set in `SPEC-08` §5.
. `ERR_SEC_304` was unreachable as written (allow = true is permitted). Now: allow and deny for the same topic, or a deny that removes nothing.
. `ERR_SEC_302` was listed as build time but described a runtime keystore check. Now an enclave-syntax and permissions-XML check; the keystore check is the runtime `ERR_SEC_101`.
. Two embedded spec manifests were not valid (missing `[interfaces]`), and the manifest schema cited a nonexistent `SPEC-13`.

== M1. Front end: ingestion to IR

Ingestion, schema check, lowering to the IR, canonical form and hashing (SPEC-00, 01, 02, 04).
The dry-run prototype (73 checks) is the starting point.

Exit: every valid corpus manifest lowers to the expected IR and hash in all three input formats. Every invalid one fails with the expected code and exit status.

Status: *done* (`src/nodesmith/manifest/`, `semantics/`, `ir/`, `api.py`; see `docs/ARCHITECTURE.adoc`). `nodesmith validate` and `lower` pass the whole corpus (`pytest`, 102 tests), independently of the reference in `conformance/reference/`. `validate` reports every error it can find, following the recovery rules of `SPEC-04` §3 (`conformance/multi/`). Lowering needs the semantic checks and callback-group assignment, so those were built here too; M2 is therefore hardening, not a first implementation.

== M2. Semantic pass

References, types, expression type-checking, parameter constraints, the conflict graph and callback-group derivation (SPEC-02, 12).

Status: *done.*

- Source positions: every diagnostic carries file, line and column (TOML, YAML and JSON) and the console form shows the source line with a caret (`SPEC-04` §4.4).
- Every code a manifest can trigger has at least two corpus cases (85 single-error cases and 8 multi-error ones), and `pytest` also asserts that each case reports exactly its one code and has a position inside the file.
- Callback groups are checked against answers worked out by hand for all eight examples, and as properties on random inputs (conflicting pipelines share a group, groups are exactly the conflict components, numbering has no gaps, the result does not depend on declaration order).
- `--format=json` output is validated against the schema printed in `SPEC-04` §4.4, read from the spec itself.

Gaps found and fixed while doing it:

. `ERR_SEM_106` was specified for `parameter_constraints`, `step`, `one_of` and `fixed_length` (`SPEC-07` §5) but only `min`/`max` were checked. All are now checked against the defaults; constraints are evaluated (`src/nodesmith/frontend/constants.py`, and independently in the reference). `step` is now defined as aligned to `min` (0 if absent).
. An inconsistent interface declaration was reported again at every use; later uses are now silent.
. `validation.regex` has no defined dialect and is not checked: recorded as a known gap.

Not covered: float32 rounding and integer wrap-around are not modelled by the reference's constraint check (the product models wrap-around, not float32 rounding).

== M3. C++ synthesis (core)

Synthesis and atomic emission for node, parameters, state, pub/sub, services, timers, startup pipelines and pipelines, plus the runtime library (`SnapshotRing`, `RunGate`, `DiagRing`, numeric helpers).

Status: *written; the ROS part is not verified.*

- `nodesmith generate` writes `CMakeLists.txt`, `package.xml` (depending on the chosen RMW only), `pipelines.hpp`, `runtime.hpp`, the node header and source, and `main.cpp`, into a temporary directory that is swapped in atomically (`src/nodesmith/generators/cpp/`, `templates/cpp_rclcpp/`).
- *Verified locally:* the pipelines (`pipelines.hpp`) are compiled with `-Wall -Wextra -Werror` and compared with a reference interpreter on random inputs, over every operator, built-in, field type and sink rule (`tests/fixtures/semantics.toml`), and the test itself is shown to catch a broken helper. The numeric helpers and the diagnostics ring have their own tests under UBSan and ThreadSanitizer. Output is byte-identical across runs, and the complete output for five examples is checked in (`tests/golden/`).
- *Verified only against a stand-in:* the ROS glue (`tests/support/ros_stub/`, drivers in `tests/cpp/drivers/`) compiles against the signatures we believe Jazzy has and behaves as specified: staged state, publication order, parameter validation and snapshots, faults and diagnostics, timers, services. The stand-in cannot tell us that real rclcpp agrees.
- *Not verified:* everything on real ROS 2 Jazzy. The `jazzy` job in `.github/workflows/ci.yml` builds the example nodes with `colcon` and runs `tests/jazzy/e2e.py` against them; it has not been run, and its first run is expected to need fixes. The sequence lives in one script, `tests/jazzy/run.sh`, driven by the list `tests/jazzy/examples.txt`; CI runs it with `--all`, and `tools/jazzy_check.sh` runs it on a developer machine in a throwaway Docker container, by default on the `smoke` subset (examples 02 and 03), and removes everything but the cached image after each run (`tools/jazzy_cleanup.sh` removes the image too).
- *Refused for now:* extension blocks (M4), `zero_copy`, parameter arrays of `int32`/`float32`, `uint64[]`/`int64[]` fields and fixed-size ROS arrays.

Exit: examples 01-03, 07 and 08 build with `colcon` and pass `tests/jazzy/e2e.py` in the `jazzy` job. This closes the ROS-side "unverified" notes for SPEC-03.

Bugs found by the differential test while building this: fused multiply-add changed `low_pass` results on ARM (now `-ffp-contract=off`, and `SPEC-02` §6 forbids fusing), and the front end widened the arguments of `len` and `to_*` to `float64`, which broke `to_int64` of a large integer and `len` of a string (fixed in the product and the reference, with new corpus cases).

=== M3b. User functions

Status: *written; the ROS part is not verified.* A manifest can declare functions (`[[functions]]`, `SPEC-01` §4.9) that expressions call (`SPEC-02` §5.1). The user writes them as plain C++ functions in a `logic/` folder (no `main()`, CMake or ROS code, plus optional `setup()` and `teardown()` hooks); `generate` copies that folder into the one self-contained package and declares the expected signatures in `logic_api.hpp`. A function the user has not written is a weak placeholder that faults loudly (`SPEC-03` §4.4). When there is no `logic/` folder, `generate` writes a starter once and never rewrites it. This added `1.1.0` to the manifest and IR (`INDEX` §7).

Checked by the conformance corpus (example 09 and nine new rejected cases), the differential test against a reference interpreter (the semantics fixture calls four functions), the generated node against the rclcpp stand-in (including a missing function), and tests of the starter, the copy, `--logic-dir` and the missing-function note. The `jazzy` job builds example 09 as one package with a real implementation (`tests/jazzy/user/speed_planner_node/`).

Not done: Python user logic (with the Python target), reading an existing C++ file written in another shape (for example without `fault`), and checking a user's signature against the manifest at build time (a mismatch leaves the placeholder in use).

== M4. C++ extensions

Lifecycle, dynamic parameters, security, telemetry probes, real-time, shared memory, and simulation and fault injection (SPEC-05 to 11), one at a time.

Exit: examples 04-06 build and pass their behavioural checks. Each SPEC "Unverified" note is either confirmed or corrected in the spec.

== M5. Python target (core)

Core first, then the extensions M0 marked as supported for Python.

Exit: the same behavioural checks as M3 and M4 pass for the supported feature set of Python.

== M6. Golden files and hardening (v1 release)

Generated-output golden tests keyed on the IR hash, determinism across machines, error-message quality, and the `bench` driver-source generation (SPEC-09).

Exit: two clean machines produce byte-identical output for every corpus manifest.

== M7. Python extensions (immediately after v1)

Lifecycle, dynamic parameters and simulation first (once verified on Jazzy), then the rest, each removing its `ERR_SEM_114` case.

== Not planned

Rust target (deferred), a configurable RMW (next phase), `frontend/` (no spec), deployment, CI, and any hardware integration.
